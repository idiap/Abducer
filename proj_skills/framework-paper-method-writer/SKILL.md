# Framework Paper Method Writer

For step-level revisions, follow [the step explanation contract](../framework-paper-workflow-appendix-writer/references/step-explanation-contract.md).
Keep one continuous, fully worked occurrence sequence in the main text: actual
input, procedure, criterion, changed output and failure consequence at each step.
For structured-description requests, use the shared contract's labeled fields:
concise purpose and named Input/Output content, with Method, Check, Next and Example
kept distinct. Put explanatory depth in the transformation and concrete case.
The appendix expands the complete inventory. A synthesis paragraph alone is not
the main-text walkthrough, and implementation uncertainty must stay explicit.

For conceptual-organization requests, follow [the shared conceptual inquiry contract](../framework-core-mechanism-curator/references/conceptual-inquiry-contract.md) and the reviewed 2.0.0 conceptual model. Make the situation, tension, diagnosis including `not_conceptual`, alternatives, reflective changes, preserved differences, plural comparison, and revision conditions the method's argument. Native operator labels are optional many-to-many supporting annotations, not a fixed sequence or universal cognitive basis. Show the source-profile six lenses through actual changes and grounded non-applicability rather than headings alone.

If this skill owns the section, merge the core writer's child material into one fresh packet; otherwise avoid duplicating its dedicated section. Preserve the continuous occurrence walkthrough and complete appendix under the prior step contract. An explanatory organization is not an execution trace.

Consume only blueprint, ledger, FunctionalCapabilityModel, WorkflowStructureModel, FrameworkAbstractionModel, and the reviewed CoreReasoningMechanismModel and child-fragment packets in this manual lane. Explain inputs, typed transformations, invariants, control flow, failure paths, and outputs at scientific abstraction level. Preserve declared versus observed semantics and blueprint notation. Do not substitute implementation inventory for method or infer runtime behavior from topology. Emit only a controlled TeX fragment and schema-valid sidecar; never read repository files.
