# Framework Reasoning Taxonomy Modeler

Produce `ReasoningTaxonomyModel` version `1.0.0` for `$framework-paper-taxonomy-plotter`. This manual paper-writing lane turns a frozen workflow source packet into two connected views: what kind of reasoning each operation performs, and which artifact types it consumes and produces. It does not modify the manuscript or add a deterministic paper-runner stage.

Read [the model contract](references/taxonomy-model-contract.md). Require a frozen `PrismWorkflowAppendixSource` from `$framework-prism-workflow-extractor`, its `RepositoryEvidenceIndex`, and requested workflow/profile scope. An indexed manuscript may supply its conceptual taxonomy; native source declarations supply native signatures. Ask the extractor to refresh missing evidence rather than expanding the frozen source boundary silently. Category and dependent-type models are optional comparison inputs and must bind to the same source digest.

1. Account for every selected workflow and occurrence, including partial, excluded, blocked, and unclassified entries. Preserve profiles, original/native disagreements, source posture, and unknown interfaces. An empty taxonomy assignment means unclassified, never permission to omit the operation.
2. Separate functional layers, reasoning families, operation occurrences, workflows, and artifact types. Repeated operation names have separate occurrence IDs. Workflows may contain many families; one family may occur in many workflows. Keep stable source IDs separate from shortened display labels.
3. For the current manuscript, inspect its four overlapping functional layers and eight primitive reasoning types. Candidate expansion groups A/I/T; consequence and behavior exposure groups D/M; discrimination groups C/R; calibration groups E. Preserve these as manuscript classifications with exact evidence, not new native type declarations or a universal cognitive ontology. Show selected taxonomy families even when no selected workflow instantiates them; zero occurrences differs from unknown classification. Allow overlaps and new or unclassified families where the selected evidence requires them.
4. Classify from an explicit family declaration where available. Otherwise record an evidence-backed interpretation as `inferred`, or a suggested change as `proposed`. Never infer reasoning from an agent's name alone. Distinguish epistemic calibration from scientific content generation and reflection motifs from new primitive families unless sources explicitly say otherwise.
5. Copy exact named input/output ports and source type expressions. Preserve nominal identity, wrapper boundaries such as `Generated[T]`, alternatives, multiport bundles, record fields, and retained inputs. An artifact type is not an agent, skill, operation, or family. Similar field shapes do not establish type equality or subtyping.
6. Model membership independently of sequence. Functional grouping is neither a subtype edge nor a happens-before edge. Include actual subtyping only with an explicit source declaration, direction, and limitations. Store workflow control/sequence separately with guards and provenance; leave actual order unknown when only membership is known.
7. Keep category bundles distinct from categorical products and DTT indices distinct from native nominal types. A proposed `Assessment(c)` refinement can be an annotated mathematical overlay, but cannot silently replace a native assessment type. A relation certificate or test result is not a proof or an automatic coercion.

Write `reasoning-taxonomy-model.json` plus a short modeling report under the isolated paper-run output root. Check ID uniqueness, reference resolution, source digest agreement, every named port, coverage, profile boundaries, and the distinction between classification and execution. Include unresolved assignments and candidate claims for `$framework-paper-claim-curator`. Hand the model to the plotter with figure scope and limitations; do not claim automatic validation or completeness beyond checks actually performed.
