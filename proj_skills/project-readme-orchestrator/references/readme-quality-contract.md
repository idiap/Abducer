# README Quality Contract

Use this order unless the repository has a stronger established product convention.

1. Project name and one-sentence promise
2. Trust boundary or important qualification
3. Conceptual model
4. Minimal installation and first run
5. Results worth opening first
6. Common next tasks
7. Architecture and extension links
8. Status and license

## Content Rules

- Let the opening answer what, for whom, and why.
- Put one runnable local path before optional providers and integrations.
- Group outputs by user decision, not by every generated filename.
- Show no more than one command example per common task in the root README.
- Link to the canonical guide for variants and operational detail.
- Keep internal skill-stack names out of the conceptual explanation unless the user is extending the framework.
- State blind-run, evidence-fidelity, and signoff boundaries near the claims they qualify.

## Review Questions

- Can a verification engineer explain the project after the first screen?
- Can a new user run the local example without credentials?
- Is the first result to open obvious?
- Does every important claim have an authoritative repository source?
- Are advanced surfaces available without interrupting the first-run path?
- Does each repeated topic have one canonical owner?

The gate should protect semantic order and verifiability. Do not enforce brevity through an arbitrary line limit when linked detail is still necessary.
