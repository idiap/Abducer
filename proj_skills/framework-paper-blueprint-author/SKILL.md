# Framework Paper Blueprint Author

Create the paper's controlled interface, not its prose.

## Inputs

- validated `FrameworkAbstractionModel`
- validated `PaperClaimLedger`
- optional validated literature snapshot and authorized result packet

Never inspect repository files or accept free-form repository summaries. Reject stale or mismatched input digests.

## Procedure

1. Select `descriptive_framework` unless eligible external literature and results justify a stronger paper kind.
2. State one thesis using accepted descriptive or interpretive claims.
3. Assign every accepted claim ID to explicit section owners; assignment is permission, not an obligation to assert it.
4. Freeze the glossary, notation, citation keys, figure/table plan, non-claims, and section order.
5. Keep appendices and reproducibility notes as blueprint-owned subsections.
6. Place the abstract first in paper order but schedule its drafting last. Limit abstract and conclusion to claims already owned by accepted body sections.
7. Run `scripts/generate_paper_packets.py blueprint ...` for deterministic packet creation and validation.

## Conceptual inquiry argument

For conceptual-organization requests, follow [the shared conceptual inquiry contract](../framework-core-mechanism-curator/references/conceptual-inquiry-contract.md) and consume `CoreReasoningMechanismModel` 2.0.0 before freezing the outline. Organize the main text around the conceptual situation, tensions, grounded diagnosis (including `not_conceptual` exit), rival primitives/relations/representations, reflective changes, preserved successes/differences, plural comparison, and consequences/revision. These are explanatory questions, not a fixed temporal workflow. Do not begin from eight operator primitives or force explanatory anchors into primitive/composition/motif kinds.

Assign the core writer one dedicated section or child fragments under the method owner. Allocate a continuous concrete case and enough space to make the six source-profile lenses informative; supporting operator annotations and formal notation follow the inquiry. Own one authoritative explanation per claim/term while licensing consistent summaries elsewhere. Preserve all frozen workflow and occurrence explanations in the appendix under the step contract; reorganizing the center does not reduce that scope. This manual blueprint supplement is not generated by the fixed-section CLI.

## Degradation

- Without a provenance-valid literature snapshot, prohibit comparative and novelty claims and assign Related Work an evidence-status narrative.
- Without an authorized result packet, prohibit efficacy and causal claims and title Evaluation `Current Evidence Status`.
- Preserve contested and unknown claims as non-claims or explicit limitations.

Output only `paper-blueprint.json`, then hand it with the ledger and approved models to section owners.

For a requested Prism workflow appendix, additionally record a scratch appendix plan
using the extractor and category-modeler packets. Author a schema-valid scratch
`PaperBlueprint` and matching curated ledger for the prompt lane; the CLI generator
does not allocate appendix ownership. Assign descriptive claim ownership,
selected workflow coverage, source exclusions, notation, diagrams and assumptions to
`framework-paper-workflow-appendix-writer`. Keep this plan separate from CLI-generated
blueprints until the fixed-section generator supports the lane. Do not turn unproved
semantic functoriality or diagram commutativity into an accepted claim.

For dependent-type-style writing, substitute `PrismWorkflowDependentTypeModel` and
owner `framework-paper-dependent-type-writer`. Allocate contexts, indexed families,
typing judgments and one explanatory derivation before prose. Distinguish native
declarations from proposed refinements and stated assumptions in claim ownership;
an assessment record is not automatically a proof term. Freeze binder names,
universe scope if used, equality notation and the manuscript insertion plan. This
writer can own a formalization section or appendix; the fixed-section CLI has no
automatic route for it.

Assign one accepted worked example to every workflow in the appendix scope using
`WorkflowExamplePlan` from `$framework-workflow-example-designer`. Specify its placement
under that workflow, allowed illustrative claims, concrete reasoning content and useful
outcome. `$framework-paper-workflow-example-writer` supplies child fragments; the existing
category or dependent writer remains the final section owner. A summary coverage table
does not replace an example, and a name-swapped generic example does not count twice.
Keep provenance in sidecars so reader-facing examples focus on the actual problem.

For taxonomy/type plots, allocate figure IDs, claims, captions, notation and placement
from `ReasoningTaxonomyModel` to `$framework-paper-taxonomy-plotter`. The main appendix
writer owns the final section. Freeze the view scope and distinguish membership,
input/output use, explicit subtyping and proposed refinements in captions and legends.
An overview may group items only when the detail view and coverage mapping preserve them.

## Mandatory step explanation gate

Read [the shared step explanation contract](../framework-paper-workflow-appendix-writer/references/step-explanation-contract.md) for occurrence-level paper revisions.

Allocate space for every occurrence explanation and one continuous main-text walkthrough. Assign exactly one final appendix owner. Do not budget detailed reasoning away in favor of inventories.

## Recursive goals and workflow relationships

When this explanation is requested, read [the shared recursive-goals contract](../framework-core-mechanism-curator/references/recursive-goals-and-workflow-relations.md). Allocate main-text explanation of recursive goals, stopping, parent return and revisitation, one continuous recursive case, and an overview with a complete workflow relationship table. Preserve sole section ownership and the complete occurrence appendix. This is a manual authoring extension, not a new fixed-runner schema or stage.
